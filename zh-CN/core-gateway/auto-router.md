# 自动路由

自动路由是一个**基于意图的模型选择层**。你不必在应用中硬编码模型，而是把请求指向一个自动路由器，它会根据用户实际提问的内容，为每条消息挑选最合适的**模型组**——随后的路由、负载均衡与故障转移机制照常接管。

{: .note }
自动路由**不是**一种路由策略。它在你在[路由与负载均衡]({% link zh-CN/core-gateway/routing.md %})中配置的策略**之前**运行——它把请求的模型改写为所选的组，然后 Router 再用常规方式为该组挑选一个健康的部署。两者相互独立，可以干净地组合使用。

---

## 工作原理

每个自动路由器包含一组**路由**。一条路由由一个目标模型组加上它应当服务的请求类型描述（以若干示例短语表达）组成。每个请求的处理流程：

1. 自动路由从请求消息中提取文本。
2. 将文本与各条路由进行匹配，选出最合适的一条。
3. 所选路由的模型组替换掉请求中原本的模型。
4. Router 继续按其常规策略（least-busy、lowest-cost……）以及[故障转移]({% link zh-CN/core-gateway/failover.md %})行为处理。
5. 如果没有路由匹配——或出现任何问题——请求会回退到路由器配置的**默认模型**。自动路由永远不会拦截请求。

每个路由器可在两种匹配模式中选择：

| 模式 | 匹配方式 | 适用场景 |
|---|---|---|
| **Performance**（默认） | 将消息与各条路由的短语做语义比对，在超过阈值的前提下选出最合适的一条。每个请求约增加 10 ms。 | 高吞吐、低开销、确定性 |
| **Advanced** | 让一个小模型把消息分类到某条路由中。能处理更细微的意图，但每个请求约增加 200–500 ms。 | 关键词/相似度匹配难以区分的场景 |

两种模式都完全运行在你的 Routero 部署内部，使用一个**内部服务账号**——匹配调用会回环经过网关自身。它们**不**消耗你的虚拟密钥预算，也**不**以你的费用调用外部供应商。

{: .note }
自动路由是静态的、由配置驱动的——它**不会**随时间学习或自适应。路由决策完全由你的路由定义、消息内容以及匹配模式决定。要改变行为，编辑路由即可。

## 定义路由

路由构建器对每条路由要求四项内容：

| 字段 | 说明 |
|---|---|
| **模型** | 该路由交棒到的目标模型**组**，从你已配置的组中选择。每个路由器中一个组只能作为一条路由的目标。 |
| **描述** | 对该路由所处理内容的简短可读说明。Advanced 模式会用到。 |
| **主题与示例** | 表征该路由的短语——输入后按回车添加。Performance 模式将进入的消息与这些短语比对。简短的描述性短语（如"物理问题""代码分析"）往往比完整的示例提示词更有效。每条路由最多 50 条，每个路由器最多 500 条。 |
| **分数阈值** | 可选（0–1）。Performance 模式下一条路由要胜出所需的最低相似度。默认 `0.2`。 |

一个分流路由器的示例路由表：

| 路由（模型组） | 说明 | 示例短语 |
|---|---|---|
| `reasoning` | 复杂推理、数学、分析 | *"证明这个定理"、"调试这个算法"、"分析其中的权衡"* |
| `coding` | 代码生成与解释 | *"写一个 python 函数"、"重构这个类"、"解释这段堆栈跟踪"* |
| `general`（默认） | 日常提问与闲聊 | *其他一切* |

![路由构建器——模型、描述、主题、分数阈值，以及可选的 JSON 预览](/assets/images/auto-router/auto-router-route-builder.png)

表单会即时校验——重复的目标、超出范围的阈值、短语数量超限都会在保存前被标出——可选的 **JSON 预览**会显示将要存储的确切内容。

## 创建自动路由器

打开 **Models & Endpoints → Add → Auto Router**。抽屉表单包含：

- **Organization（组织）** —— 路由器所属的组织。
- **Auto Router Name（名称）** —— 调用方在请求中使用的名字（见下文）。
- **Default Model（默认模型）** —— 没有路由匹配时使用的模型组。
- **Routing Mode（路由模式）** —— Performance 或 Advanced。
- **Routes（路由）** —— 用上述路由构建器搭建；至少一条，每条需有目标模型、描述和至少一个示例短语。

![Models & Endpoints 页面的 Add 菜单，其中的 Auto Router 选项](/assets/images/auto-router/add-auto-router-entry.png)

![Add Auto Router 抽屉——名称、默认模型、路由模式与路由构建器](/assets/images/auto-router/add-auto-router-drawer.png)

创建后，路由器会带上 **Auto Router** 标签出现在 Models & Endpoints 页面，同样的字段之后可在其详情视图中编辑。

## 调用自动路由器

从调用方角度看，自动路由器只是另一个模型名：就是创建时给它起的名字，与仪表板模型列表中显示的完全一致。把现有请求指向它即可：

```python
response = client.chat.completions.create(
    model="triage",                      # 路由器自己的名字——由它挑选真正的模型组
    messages=[{"role": "user", "content": "证明两个偶数之和仍是偶数。"}],
)
```

{: .warning }
**调用时只写路由器的名字（`triage`），绝不要带 `auto_router/` 前缀。** 该前缀是网关在背后存储的内部标识，不是可调用的模型名。请求 `auto_router/triage` 匹配不到任何模型，网关会把 `auto_router` 当作未知供应商，以 **Unmapped LLM provider** 错误拒绝调用。

网关为这条消息选择 `reasoning`，把请求交给 Router 进行部署选择，然后返回响应。响应中带有显示最终由哪个部署提供服务的响应头：

- `x-routero-model-id` —— 所选部署的模型 id
- `x-routero-model-api-base` —— 所选部署的 API base

![自动路由器在模型详情视图中的呈现](/assets/images/auto-router/auto-router-overview.png)

{: .note }
自动路由检查的是消息**内容**，因此对于没有消息的请求（例如透传与非聊天端点）它会跳过——这些请求会直接发往所请求的模型。

## 多租户与地域

每个自动路由器都是**按组织作用域限定**的：一个路由器属于一个组织，其路由仅对该组织的密钥解析。当你有按组织划分的模型组时，为每个组织提供各自的自动路由器并引用各自的组即可。

驱动匹配的内部模型与地域匹配，中国区工作区开箱即用国内模型：

| 地域 | Performance 模式模型 | Advanced 模式模型 |
|---|---|---|
| 中国（`cn-north-1`） | `internal-text-embedding-v4` | `internal-qwen-plus` |
| 所有其他地域 | `internal-text-embedding-3-small` | `internal-gpt-4o-mini` |

这些模型运行在内部服务账号上——不在你的模型列表中，也绝不会向你的密钥计费。

---

## 可用性

自动路由所需的一切都是标准 Routero 部署的一部分。两种匹配模式及其内部模型均已包含并在平台上运行——你无需安装或 provision 任何东西，也不需要 Redis、向量数据库或 GPU。

---

## 与网关其余部分的组合

自动路由可与网关的每一项其他能力组合使用：

- **路由与故障转移** —— 所选模型组的负载均衡与故障转移方式与任何直接请求的模型完全一致。
- **策略** —— 自动路由所路由到的模型组本身可以携带[能力策略]({% link zh-CN/core-gateway/policies.md %})（护栏、提示词、记忆、Token 节省）。
- **护栏 / 提示词 / 记忆 / Token 节省** —— 照常作用于解析后的请求。参见 [AI 能力]({% link zh-CN/advanced-features.md %})。

→ 关于自动路由器交棒之后的部署选择策略，参见 [路由与负载均衡]({% link zh-CN/core-gateway/routing.md %})。
→ 关于所选组的重试行为，参见 [故障转移与回退]({% link zh-CN/core-gateway/failover.md %})。
